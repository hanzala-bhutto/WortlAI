# Feasibility: 011 - Embedder interface + Qdrant collections via LlamaIndex

- **Issue**: #11 - **Phase**: 2 - **Date**: 2026-07-31 - **Author**: Claude (reviewed by Hanzala)

## Goal
Stand up `rag/embedder.py` as the one swappable embedding interface CLAUDE.md names alongside `llm/provider.py`, `voice/tts.py`, `voice/stt.py`, and wire a LlamaIndex ingestion pipeline that writes two Qdrant collections (`vocab`, `content`) with payload `{level, topic, chapter, type}`, so filtered semantic queries (an A2 query about Verabredungen) return relevant results. This is the retrieval half of the RAG pipeline that #9 WordRecords and #10 RedemittelSet/GrammarBox records feed into.

## Investigation
Nothing is pinned yet. `backend/requirements.txt` has no llama-index, qdrant-client, or sentence-transformers entries. `.env.example`'s header comment already names "llamaindex + qdrant-client (Phase 2)" as owed to this issue, and `docs/PLAN.md`'s directory map names `rag/embedder.py` and `rag/qdrant_store.py` but neither file exists yet (`backend/app/rag/` currently has only `glossary_parser.py` and `vision_extract.py`, both #9/#10). This is greenfield, not a refactor.

LlamaIndex + Qdrant integration (`llama-index-vector-stores-qdrant`, latest 0.10.2, released 2026-07-02): `QdrantVectorStore(collection_name=..., client=QdrantClient(url=...), enable_hybrid=False)` implements LlamaIndex's VectorStore interface; wrapped in a StorageContext it is driven the normal way (`VectorStoreIndex.from_documents(docs, storage_context=...)`). Two collections (vocab, content) means two QdrantVectorStore instances against the same QdrantClient, each with its own StorageContext/index; no single-collection multitenancy trick needed since our split is by content shape (word records vs. Redemittel/grammar chunks), not by tenant.

Metadata filtering: LlamaIndex's `MetadataFilters` / `MetadataFilter(key=..., operator=FilterOperator.EQ, value=...)` is a store-agnostic API that the Qdrant integration translates into native Qdrant Filter clauses on query(). Supported operators for this store include EQ, NE, IN, GT/GTE/LT/LTE, TEXT_MATCH. This covers level/topic/chapter/type equality and IN filters directly; no custom Qdrant client code needed for the filtering half of the acceptance criterion.

Payload indexes: Qdrant's `create_payload_index` (exposed to LlamaIndex via `QdrantVectorStore(..., payload_indexes=[...])` or called directly on the QdrantClient) speeds up filtered search on large collections, but Qdrant's own docs frame this as a performance optimization for filters over large payloads/high cardinality, not a correctness requirement; unfiltered or unindexed-field filtering still returns correct results, just with a full scan. At under 10k vectors (the same corpus-size premise docs/PLAN.md already used to justify Qdrant-over-sqlite-vec on integration grounds, not performance), a full scan per query is sub-millisecond-to-low-millisecond. Explicit payload indexes are not necessary at this scale and can be deferred until a slow-query problem is actually observed.

multilingual-e5-large prefixing: confirmed still accurate. `intfloat/multilingual-e5-large`'s own model card requires "query: " prepended to search queries and "passage: " prepended to indexed text; omitting this measurably degrades retrieval (this is a documented, not folklore, requirement - the HF discussion threads confirm it is still enforced in the current checkpoint, not just an old README artifact). LlamaIndex's `HuggingFaceEmbedding` (`llama-index-embeddings-huggingface`) wraps sentence-transformers and exposes exactly this hook: `query_instruction`/`text_instruction` constructor params, so `HuggingFaceEmbedding(model_name="intfloat/multilingual-e5-large", query_instruction="query: ", text_instruction="passage: ")` is the correct call, not a bare `HuggingFaceEmbedding(model_name=...)` (which uses the class's own generic default instructions, silently wrong for e5). Embedding dimension: 1024.

NIM embeddings API: yes, NIM has an OpenAI-compatible /v1/embeddings endpoint backed by NeMo Retriever models. **Spike run 2026-07-31** (live call against the project's own NIM key): the model this report originally named, `nvidia/llama-3.2-nv-embedqa-1b-v2`, is dead - HTTP 410, "reached its end of life on 2026-05-18." Listing `/v1/models` and probing candidates found the working current model: **`nvidia/nv-embedqa-e5-v5`** (an E5-family NIM-hosted model), which returned HTTP 200 with a 1024-dim embedding for a German test string once two required fields were supplied: `input_type: "query"|"passage"` (missing it fails with `"'input_type' parameter is required for asymmetric models"`) and `truncate: "NONE"` (omitting it triggers a generic 400 `"error parsing the body"` with no hint at the real cause - undocumented in the error message, only found by trial). Usage reporting works (`prompt_tokens`/`total_tokens`). This is free-tier-consistent with the rest of NIM usage already accepted in this project (vision/fallback LLM), same risk posture, now live-confirmed rather than assumed. Critically, the asymmetry mechanism is different from e5's text-prefix convention: NIM's embedding model uses request-level `input_type` and `truncate` fields, not a string prefix baked into the text. An embedder abstraction that only knows "prepend a string" would silently do the wrong thing (or nothing, or 400) if swapped to NIM; the interface needs a mode parameter that each implementation maps to its own convention (string prefix for e5, input_type/truncate fields for NIM), not a leaky prefix-string parameter. Bonus finding: `nv-embedqa-e5-v5`'s 1024-dim output matches local e5-large's dimension exactly, so both providers can share one Qdrant collection vector-size config - a swap still means re-ingesting (different models' vectors are not directly comparable under cosine similarity even at equal dimension), but it removes the "collection has to be resized" failure mode this report worried about below.

llm/provider.py precedent: its swappability pattern is a fallback chain built from _Target dataclasses and one _complete_one method reused per link, selected by which API key is present (_build_chain). Embeddings do not need a multi-link retry chain the same way: there is no per-request fallback mid-query the way a chat completion can degrade to another model, since a missing embedding is a hard failure, not something to paper over with a worse model, because query and passage vectors must come from the same model or cosine similarity is meaningless. The right analogue is llm/provider.py's config-driven selection idea, not its retry chain: one interface, one concrete implementation instantiated at startup based on a .env switch, same as how tts.py picks edge-tts vs. Qwen3-TTS.

## Approach

Recommended interface (`rag/embedder.py`, a Protocol not an ABC; no shared state or template method between implementations, just a shape both must satisfy, consistent with vision_extract.py's existing use of Protocol for its own extraction interface):

- `class Embedder(Protocol)`: a `dimension: int` attribute (so callers/collection-creation code can assert compatibility) and an async `embed(texts: list[str], mode: "query" | "passage") -> list[list[float]]` method.

Two implementations: `LocalE5Embedder` (wraps HuggingFaceEmbedding with the query_instruction/text_instruction params above, dimension = 1024) and `NIMEmbedder` (a direct httpx2 call to `{nim_base_url}/embeddings` with `model=nvidia/nv-embedqa-e5-v5`, `input_type` per mode, `truncate="NONE"`, dimension = 1024 - spike-verified 2026-07-31, see Investigation). A new `Settings.embedder_provider` (local-or-nim, or reuse the existing empty-key-means-unavailable pattern: default to local, require nim_api_key if NIM is selected) plus `Settings.embedder_model` picks the implementation at get_settings()-read startup, mirroring nim_vision_model's no-default-fails-at-boot convention. A factory function `get_embedder(settings) -> Embedder` is the one call site everything else in rag/ depends on, same shape as llm/provider.py being the one place that talks to an LLM.

Alternatives considered

1. LlamaIndex's built-in `Settings.embed_model` global (set once, every VectorStoreIndex call picks it up implicitly): rejected because it is LlamaIndex's own ambient global state, not an explicit interface behind one file, harder to unit-test with a fake embedder, and CLAUDE.md's guardrail is explicitly "keep external deps behind one file," which an implicit global works against. rag/embedder.py can still hand its chosen instance to Settings.embed_model internally if convenient for LlamaIndex's ingestion pipeline plumbing, but the public interface the rest of the app imports must be the explicit Embedder/get_embedder(), not the LlamaIndex Settings singleton directly.
2. String-prefix-only interface (an `embed(texts, prefix: str)` signature, asking every caller to know and pass the prefix literally): rejected because it silently breaks the moment NIM is selected (NIM does not use a text prefix, it uses the input_type request field), reintroducing exactly the kind of provider-specific leakage llm/provider.py was designed to hide. The mode enum keeps the query/passage asymmetry concept, which is genuinely shared across both models, without leaking either model's specific mechanism to callers.

## Risks & unknowns

- Dimension mismatch: resolved by the spike - both e5-large (local) and `nv-embedqa-e5-v5` (NIM) are 1024-dim, so Qdrant collections don't need per-provider vector sizes. Swapping embedder_provider still means re-ingesting from scratch into fresh collections (vectors from different models are not comparable under cosine similarity even at equal dimension), but there's no forced resize.
- NIM embeddings model name in the original report (`nvidia/llama-3.2-nv-embedqa-1b-v2`) was wrong - EOL as of 2026-05-18 (HTTP 410). Corrected to `nvidia/nv-embedqa-e5-v5`, live-verified 2026-07-31 (HTTP 200, 1024-dim, German test string). Two required request fields were undocumented-by-error-message and found only by trial: `input_type` ("query"|"passage", required for asymmetric models) and `truncate: "NONE"` (its absence produces a generic "error parsing the body" 400 with no indication which field is missing) - `NIMEmbedder` must always send both.
- e5 local inference needs a model download and CPU/GPU decision: sentence-transformers will pull the roughly 1.1GB e5-large checkpoint from HuggingFace Hub on first run and run it on CPU by default (no GPU assumed in this project's deployment story per CLAUDE.md's single-FastAPI-service model); embedding latency for ingestion-time batch jobs is fine, but this is a new, non-trivial local dependency (torch plus sentence-transformers) that requirements.txt does not carry yet; worth flagging as a meaningfully heavier install than anything else in the stack so far.
- Guardrail 6 (untrusted content) applies to ingestion, not just LLM prompts: text embedded into vocab/content collections originates from #9/#10's already-Pydantic-validated records, so the injection surface is narrower than raw OCR text reaching a classifier prompt, but if #11's pipeline embeds raw chunk text before or alongside structured fields, the same instruction-pattern quarantine #10 built should gate what gets indexed, not just what gets classified.
- Payload index deferral is a call to revisit, not a permanent decision. If topic/chapter cardinality grows much beyond what a Netzwerk A2/B1 corpus implies, or #12's lexical-graph queries start compounding multiple metadata filters per call, create_payload_index is a one-line addition to QdrantVectorStore's payload_indexes param, not a redesign.

## Free-tier impact
No LLM/STT/TTS calls in this issue; it is local embedding inference (free, CPU-bound) or NIM embedding calls (if that path is chosen), which do not touch the Groq chain at all. NIM embedding-call volume for ingesting #9's glossary (thousands of A1 words) plus #10's Redemittel/grammar records is small and one-time per ingestion run, not per-session, so no ongoing free-tier pressure once ingestion is done.

## Effort estimate
M (0.5-1 day). Two straightforward Embedder implementations behind one interface, two QdrantVectorStore-backed collections, and a MetadataFilters-based filtered-query acceptance test. Main time sink is likely the local e5 first-run download/setup and writing the acceptance-criteria test (index a handful of #9/#10-shaped records, assert a topic/level-filtered query returns only matching content) rather than the LlamaIndex/Qdrant wiring itself, which is well-documented and low-risk at this corpus size.

## Verdict
GO, with one pre-implementation spike recommended: a live NIM embeddings call to confirm free-tier availability and actual response shape, the same discipline #10's report used before trusting nemotron-parse's documented behavior. The Embedder Protocol with a query/passage mode, two-collection QdrantVectorStore setup, and LlamaIndex's native MetadataFilters cover the acceptance criteria without new custom infrastructure; the only genuine risk is dimension lock-in once a collection exists, which is manageable by treating embedder swaps as re-ingestion, not migration.
