# Feasibility: 010 - Vision extraction (Netzwerk Kursbuch Redemittel and grammar boxes)

- **Issue**: #10 - **Phase**: 2 - **Date**: 2026-07-31 - **Author**: Claude (reviewed by Hanzala)

## Goal
Extract Redemittel sets (fixed conversational phrases, e.g. `etwas vorschlagen`/`zusagen`/`absagen`) and grammar boxes from the Netzwerk Neu A2 Kursbuch's scanned pages into Pydantic-validated, structured records - the exact "chunks, not words" units #14's FSRS cards need and #12's lexical graph consumes, per CLAUDE.md's pedagogy rules and docs/PLAN.md's RAG design (`rag/vision_extract.py`, named there already). Unlike #9's glossary PDFs, these pages carry no extractable text layer at all, so a vision-capable model has to do the reading.

## Investigation (PDF actually opened, not assumed)

Full per-page scan with pdfplumber against the real files in `Deutsch_Books/kursbuecher/` (gitignored, inspected locally only), same method as #9:

- `Netzwerk Neu A2 Kursbuch.pdf` (176 pages) - every single page has `page.chars == 0` and `extract_text()` returns empty; `page.images` ranges 1-27 per page. Fully image-based end to end, not a sampling artifact. This is the file issue #10 names.
- `A2 Ubungbuch.pdf` (202 pages) - 197 of 202 pages have `page.chars == 0`; only 5 pages (front matter/table of contents) carry real text. Effectively the same problem as the Kursbuch, but out of scope for #10 as written (issue title says "Kursbuch"); flag as a likely fast-follow once #10's pipeline exists, not bundled in.
- `Adjektiv-Endungen.pdf` (1 page) - has a real text layer (`page.chars > 0`). Does not need vision; a plain `extract_text()` pass would do, worth a one-line note so nobody defaults it into the vision pipeline out of habit.
- Only one genuine Kursbuch exists on disk: `Deutsch_Books/kursbuecher/Netzwerk Neu A2 Kursbuch.pdf`. The A1 directory (`Deutsch_Books/klett/netzwerk/A1/transkripte/`) holds only audio transcripts, not an A1 Kursbuch - not a gap for now since Hanzala is already A2, but worth knowing if a future issue tries to reuse this pipeline for A1 material that doesn't exist yet.

`backend/app/rag/glossary_parser.py` (#9) is the established pattern to match: Pydantic `WordRecord`/`VerbForm` models, `needs_review: bool` flag instead of silently guessing, `source_page` for citation/audit, deterministic-first with an LLM-assisted fallback path gated by the same guardrail-1 parse-and-validate discipline. #10's models (`RedemittelSet`, `GrammarBox`) should carry the same `source_page`, `needs_review`, and an `extraction_method` field for the same reason.

`backend/app/llm/provider.py`'s `LLMProvider` already implements the fallback chain (Groq primary/secondary -> NIM), retry-with-backoff on 429/5xx, and Pydantic-friendly JSON handling this issue should reuse rather than stand up a second HTTP client. Its `_payload`/`messages` are currently typed `list[dict[str, str]]` (plain string content) - vision calls need OpenAI-style multipart content (`[{"type": "text", ...}, {"type": "image_url", ...}]`), which is a schema extension to the existing client, not a new one.

Groq currently has no usable free-tier vision model: `llama-4-scout-17b-16e-instruct` (Groq's only vision-capable model) was deprecated for free/developer tier on 2026-06-17 per Groq's own deprecation notice, and its documented replacements (`openai/gpt-oss-120b`, `qwen/qwen3.6-27b`) are text-only. This confirms CLAUDE.md's framing that NIM is the vision provider here, not a fallback-after-Groq-vision - there is currently only one link in this particular chain.

NVIDIA NIM (`build.nvidia.com`, same `NIM_BASE_URL=https://integrate.api.nvidia.com/v1` already in `.env.example`) ships two document-relevant vision options:
- `nvidia/nemotron-parse`: purpose-built document-parsing VLM. `markdown_bbox` tool returns an array of `{bbox: [xmin,ymin,xmax,ymax] (0-1 normalized), text, content_type}` blocks (`content_type` examples: `Section-header`, `Text`, `Page-footer`) - i.e. real OCR + layout, not free-form captioning. Constraints: one image per request, no text input alongside the image, no system message, only one tool per call. **Correction from the live spike below**: this pre-spike research (self-hosted NIM container docs) describes `bbox` as a plain `[xmin,ymin,xmax,ymax]` list, but the actual hosted `integrate.api.nvidia.com` endpoint returned a `{"xmin":...,"ymin":...,"xmax":...,"ymax":...}` dict on both spiked pages. The implementation accepts either shape rather than trusting one snapshot against a versioned, moving API.
- `meta/llama-3.2-90b-vision-instruct`: general chat-vision model (OpenAI-compatible `/chat/completions`, same base URL), good for captioning/VQA-style prompts but not purpose-built for verbatim transcription of dense typeset text.

## Approach options

1. **Recommended - two-stage pipeline behind a new `rag/vision_extract.py`**: stage 1 calls `nvidia/nemotron-parse` (`markdown_bbox`) per rendered page image (implemented via pdfplumber's own `page.to_image()`, not PyMuPDF as this section originally proposed - it's the same rasterizer #9 already depends on, so no new library) to get layout-tagged, verbatim-transcribed blocks with bounding boxes; stage 2 feeds those blocks as a delimited data block (guardrail 6) to the existing `LLMProvider.complete()` on the normal Groq/NIM text chain, asking it to classify and structure blocks into `RedemittelSet`/`GrammarBox` Pydantic models, citing `source_page` and the bbox as the traceable "citation" guardrail 5 wants for anything written to the graph. Separating OCR from classification means a wrong output is attributable to one stage, so accuracy can be measured per-stage with a gold set the same way #9 measured stress-mark reconstruction separately from field regexes. Malformed stage-2 JSON retries once then the page is skipped and flagged `needs_review=True`, per guardrail 1 - never a raw LLM string reaching the DB.
2. **Single-call vision-chat extraction** (`llama-3.2-90b-vision-instruct`, one prompt asking directly for Redemittel/grammar JSON per page): loses because it conflates OCR and semantic classification in one opaque call, general vision-chat models are documented to paraphrase/summarize dense text rather than transcribe verbatim (exactly wrong for Redemittel, which must be the exact fixed phrase, not a gloss of it), and there is no bounding-box citation for guardrail 5. Worth keeping as a same-provider fallback if `nemotron-parse` errors mid-batch, not as the primary path.
3. **Local OCR + hand-rolled layout heuristics** (Tesseract/EasyOCR + colored-box detection off raw pixels, no vision-LLM): loses on the same grounds the Neo4j rejection used - unmeasured-need complexity when a maintained, documented product (`nemotron-parse`) already does layout classification for free-tier API cost. Also risks reintroducing the "no model training / no custom CV code" line CLAUDE.md already drew, and German OCR quality against Klett's colored Redemittel-box typesetting is unverified without its own spike, whereas `nemotron-parse`'s quality is at least documented for this exact task class.

## Risks & unknowns

- `nemotron-parse`'s content-type taxonomy has no "Redemittel-box" or "grammar-box" label (only generic tags like `Section-header`/`Text`) - stage 2's classification prompt is doing real semantic work and is unverified against the actual A2 Kursbuch layout in this research pass (no live API call made; NIM key is present in `.env` so a real spike is cheap). Mitigate by hand-labeling a ~15-20 page gold set spanning several Kapitel (following #9's stratified-sample method) before trusting bulk output, and gate on a checked-in baseline the way `eval_glossary_parser.py` does.
- Rate limit is a community-observed ~40 rpm, not a published NVIDIA SLA - 176 Kursbuch pages fit comfortably in an overnight batch even throttled well below that, but the batch job must treat 429s via the same retry/backoff `llm/provider.py` already implements, extended to accept image content parts rather than forking a second client.
- Untrusted-content guardrail (#6): OCR'd textbook text can contain imperative-mood German sentences (e.g. a Redemittel example like "Schreib mir eine Nachricht") that must never be read as an instruction to the extraction agent - the stage-2 prompt must keep OCR output in a delimited data block and the pipeline must scan for instruction-like patterns before indexing, same as any other ingested text.
- Scope boundary: `A2 Ubungbuch.pdf` is 197/202 pages image-only too, same problem class, but the issue as written names only the Kursbuch - confirm with Hanzala whether #10 should cover it or whether it is a deliberate fast-follow once the pipeline exists.
- API surface may have moved: NIM's VLM container has versioned, breaking release notes (checked against v1.5.0 docs); re-verify the exact `tools` schema against whatever version is live at implementation time rather than trusting this report's snapshot.
- Copyright: extracted JSON derived from Klett's copyrighted pages stays in `backend/data/` (gitignored), same rule #9 already established - never in the public repo or this report.

## Free-tier impact
NIM only for the vision calls (no Groq vision model currently exists on free/developer tier - see investigation above). One-time offline batch job: ~176 `nemotron-parse` calls (one per Kursbuch page) plus ~176 Groq text-classification calls for stage 2 - negligible against Groq's ~1,000 req/day budget and comfortably inside NIM's community-observed rate ceiling if throttled overnight. Zero Whisper/audio-seconds impact (this is ingestion, not the voice loop). Each call gets a Langfuse trace on the self-hosted instance per the LLMOps design - no metered quota concern there.

## Effort estimate
L (1-2 days). Main cost driver: building and validating the two-stage pipeline (page rasterization, `nemotron-parse` wrapper, gold-set hand-labeling across several Kapitel to catch rare box layouts, the stage-2 classification prompt + `RedemittelSet`/`GrammarBox` Pydantic schemas, and extending `llm/provider.py`'s message shape to carry image content), not the API calls themselves. The `needs_review`-flag-plus-gold-set-eval pattern from #9 carries over directly and saves time there.

## Spike results (2026-07-31)

Ran live `nemotron-parse` calls against the hosted `integrate.api.nvidia.com` endpoint using the NIM key in `.env`, on two representative Kursbuch pages (p.70: "Gut gesagt" Redemittel + "Anrufer/in"/"Firma" phrase-list boxes; p.130: a Verben-mit-Präposition grammar box plus a 3x3 Redemittel table with "einen Vorschlag machen"/"um etwas bitten"/"einen Gegenvorschlag machen" columns).

- **Request schema correction**: the report's assumed request shape was wrong in one detail. The hosted endpoint rejects a `{"type": "text", ...}` content part with the `<predict_bbox>...` control-token string (that's the self-hosted-container invocation style) - `400 Content cannot be a plain string`. The hosted API instead takes `tools: [{"type": "function", "function": {"name": "markdown_bbox"}}]` with an image-only `content` array (OpenAI-client style, per NVIDIA's own docs example). Once corrected, both calls returned `200` on the first try.
- **Transcription quality: verbatim and accurate**, including German umlauts/ß, pipe-delimited phrase lists (p.70's "Kann ich bitte mit Herrn/Frau ... sprechen? | Können Sie mich bitte mit Herrn/Frau ... verbinden? | ..." reproduced exactly), and a markdown table for p.130's 3x3 Redemittel grid (`\begin{tabular}{ccc}` with `**einen Vorschlag machen**` etc. as bolded headers, all cell phrases intact). No paraphrasing observed anywhere in either page.
- **Confirms the predicted risk**: `content_type` has no Redemittel/grammar-box label. p.130's Redemittel grid came back as `Table`; its grammar box ("Verben mit Präposition... sich freuen auf + Akk...") came back as `Caption`; p.70's Redemittel titles ("Gut gesagt: Rückmeldung geben", "Anrufer/in", "Firma") came back as `Section-header` while their phrase bodies came back as plain `Text`. So the same box type gets a different generic tag depending on whether the source layout is columnar (-> Table) or running text (-> Text/Caption) - stage 2's classification prompt cannot key off `content_type` alone and must reason over the actual text content, confirming the two-stage split was the right call.
- Tip-box icons ("!") came back as `Picture` blocks with a stray literal `"!"` for text - harmless (stage 2 will just drop content-type `Picture` blocks with no useful text), but worth a one-line filter in the parser rather than passing them to the classifier.

## Verdict
**GO**. The pipeline shape (nemotron-parse for OCR+layout, existing `LLMProvider` for classification, both guardrail-1/5/6 compliant) is confirmed sound on live data: verbatim transcription quality is high and the classification gap is exactly where predicted, with no surprises large enough to change the approach. Proceed to full implementation using the corrected `tools`-based request schema above; build the stage-2 classification gold set from a stratified sample (several Kapitel, both Table- and Text/Section-header-shaped Redemittel layouts) per #9's method before trusting bulk output.
